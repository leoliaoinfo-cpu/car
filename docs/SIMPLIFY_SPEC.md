# 業務系統全面精簡規格（交給 AI 逐階段執行）

> 版本：2026-11-12。狀態：**只有分析，尚未依本規格改任何程式**。
> 基準程式：分支 `claude/car-sales-handoff-sht2ks`，commit `adb9aa7`（DB v12，單元測試 175 項）。
> 執行者開工前先讀 `CLAUDE.md`，再讀本檔。每個階段獨立可交付、可上線、可回退。
> 最高原則：**降低每天的操作步數**。把功能換個位置擺不算完成，必須達到 §8 的步數驗收。

## 0. 使用者與不可違反的限制

- 使用者：一位 KIA K2500 貨車業務，非工程師，主力手機（390×844），其次平板。
- 他的原話：「之前太複雜沒辦法落實實際操作」「要直覺化，好好追蹤客戶進展、案件追蹤、報價追蹤」。
- 已確認的決定：主選單為「今天、案件、報價、客戶」；內部成本用**數字密碼**保護；開發分支照舊。
- 硬限制：
  1. 不刪既有資料、不改 DB 版本、不新增 store、不改既有欄位名稱（只可新增選填欄位）。
  2. 不破壞同步（`utils/dataMerge.js` 的合併規則）、儲存隔離、成交↔案件關聯（一律 `findDealForCase`）。
  3. 成本／利潤／利率／貸款公司／內部需求備忘不得出現在客戶報價預覽與 PNG。
  4. 不加新功能；只能合併、收納、移除入口、減少步驟。
  5. 背景自動化必須保留（見 §3.4）。
  6. 所有寫入走 `context.jsx`；刪除用 `ConfirmDeleteButton`；寫入按鈕要有送出中鎖定。

### 1.2 資料與關聯（store 名稱照舊）

- `clients`：基本資料、`log`（互動時間軸）、`todos`（客戶待辦）、`nextDate`（客戶層追蹤日，舊）、分類／階段／自訂欄位。
- `cases`：`clientId`、`pipelineStage`（new／follow_up／won／delivery／completed）、`nextFollowUpDate`、`quoteIds`、`dealId`（舊關聯）。一位客戶可有多筆進行中案件。
- `quoteDrafts`：報價，可無客戶；狀態在畫面上分 待成交／成交報價／未採用／未歸入案件／回收。
- `deals`：成交；`caseId`（新）、`quoteId`、`stockItems`（配件核對）、`deliveryWorkflow`（施工 SOP）。
- `workItems`（案件待辦）、`tasks`（中央待辦）、`activities`（案件互動）、`timers`（計時提醒）、`events`（行事曆活動）。
- `pricingRecords`（成本利潤）、`suppliers`、`receptionSessions`、`photos`（僅本機）、`settings`。

### 1.3 「今天」的三套來源

| 畫面 | 讀什麼 | 缺什麼 |
|---|---|---|
| 工作頁 | `buildWorkQueue`：案件追蹤日、workItems、tasks、client.todos、配件缺貨警示、施工步驟 | 不含 timers、紀念日、客戶層追蹤日 |
| 完整工作總覽（TodayPage） | 客戶狀態（追蹤規則）、客戶層追蹤日、timers、tasks、client.todos、紀念日、本日成果 | 不含案件追蹤日與 workItems（實測：明天有 4 件，這裡只顯示 1 件） |
| 行事曆 | 客戶層追蹤、timers、成交、活動、紀念日、tasks | 同上 |

### 1.4 追蹤規則、通知、待辦的實際依賴

- **追蹤規則**（`settings.crmThresholds`，冷掉／久未聯繫天數）：只影響客戶狀態燈號與篩選，使用處為客戶頁、完整工作總覽、行事曆。**不影響工作頁佇列**。
- **通知**（`notify.js`）：只在 `TimerModal` 發現 timers 到期時發出，內容只有數量。**案件追蹤日、待辦、配件再追日到期都不會發通知**。背景定時檢查只在 Android 安裝版有效。
- **待辦有四套**：`workItems`、`tasks`、`client.todos`、`timers`，各有自己的新增入口，都有日期。
- **互動紀錄有兩套**：`client.log` 與 `activities`，部分畫面兩邊都寫。
- **追蹤日有兩套**：`client.nextDate` 與 `case.nextFollowUpDate`；客戶頁已寫明「追蹤日由案件管理」，但 `nextDate` 仍有 24 處程式引用。
- **階段有兩套**：客戶的 9 階段（設定→客戶階段）與案件的 5 階段。

## 2. 重複與操作問題清單

來源標示：〔實測〕＝手機尺寸實際操作；〔碼〕＝讀程式確認；〔報告〕＝審查報告指出，本規格未逐條重驗。

1. 〔實測〕「今天」三個畫面答案不一致（§1.3）。
2. 〔碼〕報價入口 6 處：頂部報價、更多→報價管理、＋→建立報價、案件內報價區、接待→帶入報價、客戶詳情→報價單。
3. 〔碼〕建立成交 2 條路：報價管理「確認此報價成交」與客戶詳情「建立成交案」（後者自動抓最新報價）。
4. 〔碼〕交車紀錄與自動回訪提醒只在客戶詳情的舊表單；施工 SOP 在案件與「成交與施工管理」兩處可改同一份資料。
5. 〔實測〕施工進度被數字密碼擋住，新裝置沒有首次設定、沒有提示，流程走不下去。
6. 〔實測〕報價表單高 3,600–5,100px，強制確認 27 個配件分類，每次出圖／存檔跳原生確認 2–3 次。
7. 〔實測〕從案件開報價會被帶到報價管理，存完不回案件。
8. 〔實測〕新建案件必填追蹤日，並產生兩張同日重複待辦。
9. 〔實測〕施工每步二次確認，5 階段約 10 次點擊加 4 次關提示條；提示條蓋住下一個視窗的按鈕。
10. 〔實測〕缺 2 項配件仍可完成交車且無提醒；完成後卡片同時顯示「已成交」「案件已完成」「尚缺配件」。
11. 〔實測〕手機上 ⏱ 膠囊壓在 ＋ 正中央；首次啟動橫幅用語艱澀且關不掉；客戶頁搜尋框被擠到 46px。
12. 〔碼〕案件清單有三份：案件頁、客戶頁的案件流程看板、客戶詳情內。
13. 〔報告〕用語不一：配件／配備／選配／選購配備／品項；廠商／供應商／合作廠商；客戶／客戶資料／客戶追蹤；垃圾車／回收筒；儲存鈕三種名稱。
14. 〔碼〕待辦四套、互動紀錄兩套、追蹤日兩套、階段兩套（§1.4），是「同一件事要輸入兩次」的根源。
15. 〔碼〕通知只涵蓋 timers，與使用者最在意的「案件追蹤、報價追蹤」無關。

## 3. 功能分類：保留／合併／收納／移除入口

### 3.1 保留在主畫面（每天用）

今天的工作清單、案件清單與案件詳情、報價清單與報價編輯／出圖、客戶清單與基本資料、＋快速新增、案件快搜、配件核對表、施工 SOP、確認交車。

### 3.2 合併（消除重複輸入）

| 合併什麼 | 合併成 | 作法（不改 store） |
|---|---|---|
| 工作頁＋完整工作總覽＋行事曆 | 「今天」一頁，清單／月曆兩種檢視 | 月曆讀同一份佇列；TodayPage 的獨有內容併入佇列或移除入口 |
| 追蹤日兩套 | 以 `case.nextFollowUpDate` 為準 | UI 不再提供修改 `client.nextDate`；沒有進行中案件的舊客戶，其 `nextDate` 仍以唯讀項目進佇列 |
| 待辦四套 | 畫面只有一個「加待辦」 | 在案件內寫 `workItems`，不在案件內寫 `tasks`；既有 `client.todos`、`timers` 繼續讀取與可完成，但不再提供新增入口（自動回訪提醒除外） |
| 互動紀錄兩套 | 一個「記錄聯繫」動作 | 一次寫入、顯示時合併兩個來源；既有紀錄全部照舊顯示 |
| 階段兩套 | 只顯示案件 5 階段 | 客戶 9 階段的畫面入口收起；資料不動 |
| 建立成交兩條路 | 只留「指定報價成交」（`confirmQuoteDeal`） | 移除客戶詳情的「建立成交案」入口 |
| 交車紀錄兩處 | 施工 SOP 最後一步「確認交車」 | 沿用既有回訪提醒產生邏輯，需防重複 |
| 案件清單三份 | 案件頁一份 | 客戶詳情只列該客戶的案件連結；移除客戶頁看板入口 |
| 報價入口六處 | 兩處：案件內、「報價」分頁 | 其餘入口導向這兩處；接待「帶入報價」保留為資料帶入，不另開第三種畫面 |

### 3.3 收納到次要入口（右上角齒輪，不佔主選單）

- **常用設定**：報價選單（車型、配件、優惠、貸款期數、浮水印）、雲端同步、備份還原。
- **工具**：產品型錄、客戶接待、K2500 與競品比較、車高試算、業績與成本（數字密碼）、廠商名冊。
- **進階設定**：客戶分類、客戶階段、產業選項、自訂欄位、業績欄位、待辦範本、追蹤規則、通知、後台密碼、車高參數、使用說明。

「工具」哪些要留在主畫面，取決於 §9 待查證第 1 項（使用者實際使用頻率），目前不知道。

### 3.4 必須保留的背景自動化

雲端同步（防抖上傳、60 秒與切回前景下載）、每日資料保養、交車後自動建立 3／7／30 天回訪與年度提醒、交車日 ≤7 天且缺配件的「交車將近」警示、待廠商確認需排再追日、案件編號、舊資料相容整理、報價草稿保護、Service Worker 更新。

### 3.5 移除入口（資料與程式先保留）

完整工作總覽、更多頁本身、客戶頁案件流程看板、客戶詳情內的建立報價／建立成交案／預計交車日／交車舊表單／計時提醒新增、桌面與手機不同的分頁名稱。

## 4. 新版資訊架構

```
底部：今天 ｜ 案件 ｜ 報價 ｜ 客戶          右上：🔎 搜尋   ⚙ 設定與工具
浮動：＋（新增客戶／新增案件／建立報價）   ← 只留一顆浮動鈕
```

### 4.1 今天

- 頂部一行：日期＋三個可點的數字（逾期／今天／接下來）。右側切換「清單｜月曆」。
- 卡片：客戶名、要做的事（白話）、日期；**一個主按鈕＋「延後」**（明天／3 天／選日期）。點卡片進案件。
- 佇列來源：案件追蹤日、案件待辦、一般待辦、既有客戶待辦、配件缺貨與再追日、施工步驟、交車日、到期提醒與紀念日、**太久沒追的案件**（無追蹤日且 14 天以上無互動）。
- 首屏 390×844 至少看得到 4 張卡。

### 4.2 案件

- 清單每張卡一行追蹤資訊：階段、幾天沒聯絡、下次追蹤日（逾期紅字）、「已報價 N 天未回覆」。
- 篩選列：全部／要追蹤／已報價／已成交／已交車（對應既有 5 階段，不新增階段）。
- 案件詳情是**唯一工作台**，由上到下：客戶與一鍵撥號 → 階段 → 下一步與日期 → 記錄聯繫 → 報價 →（成交後）配件核對 → 施工進度 → 確認交車 → 歷程。

### 4.3 報價

- 清單卡：客戶、車型、總價、已報價天數、狀態。未歸戶的卡片直接有「歸入客戶」（可搜尋）。
- 編輯：要項在前（車型、配件、優惠、貸款、總價），少用的收進「更多選項」；底部固定「儲存」「預覽／出圖」；沒有分類逐一確認、沒有原生確認視窗。
- 從案件開的報價，存檔或成交後回到該案件。

### 4.4 客戶

- 清單：搜尋框全寬；顯示姓名、電話、進行中案件數、下次追蹤日。
- 詳情只留：基本資料、案件清單（連到案件）、照片、紀念日、歷程（唯讀彙整）。

### 4.5 設定與工具

三組：常用設定／工具／進階設定（§3.3）。內部金額畫面首次使用顯示「請設定數字密碼」。

## 5. 從洽談到交車的完整流程（目標步數）

| # | 情境 | 操作 | 目標點擊 | 現況〔實測〕 |
|---|---|---|---|---|
| 1 | 客戶上門 | ＋ → 新增案件（同表單建客戶，姓名必填，追蹤日預設 3 天後） | ≤5 | 5，但追蹤日必填 |
| 2 | 報價 | 案件 → ＋報價 → 選車型、配件、貸款 → 儲存 → 出圖 | ≤12，捲動 ≤2 屏 | 約 19，捲約 6 屏，確認視窗 2–3 次 |
| 3 | 追蹤 | 今天 → 卡片主按鈕「記錄聯繫」→ 選結果與下次日期 | ≤3 | 未量測 |
| 4 | 成交 | 案件 → 該報價「確認成交」→ 確認 | ≤3 | 4（要到報價管理） |
| 5 | 配件 | 案件 → 配件核對：備妥一鍵；待廠商直接填再追日 | 每項 ≤2 | 約 9（兩項） |
| 6 | 交車日 | 案件 → 交車日 | ≤3 | 3 |
| 7 | 施工到交車 | 逐步一按 → 最後「確認交車」 | ≤8 | 約 18–20 |
| 8 | 售後 | 自動出現在今天（3／7／30 天回訪） | 0 | 0（但只能從客戶頁舊表單觸發） |

同一筆資料只輸入一次：客戶資料在第 1 步；車型與配件在第 2 步；之後的成交、配件核對、施工都由前一步帶入。

## 6. 分階段改版計畫

共通規則：每階段單獨分支 → 單元測試全過 → `npm run build` → 手機尺寸實測並截圖 → 更新 `CLAUDE.md` → 合併。階段之間不得同時改同一檔案的同一區塊。上線前提醒使用者先手動備份一次。

### 階段 0：盤點既有半成品（先做）

- 有三條**未合併、未上傳**的本機分支含部分成果：`simp/quote`、`simp/delivery`、`simp/work`（各 1–2 筆 commit，另有未提交修改）。它們只存在目前的雲端工作環境，環境回收就會消失。
- 動作：逐條檢視內容是否符合本規格，可用的併入對應階段，不符的捨棄。
- 驗收：三條分支各有明確結論（採用／部分採用／捨棄），且不留未提交修改。

### 階段 1：導覽骨架

- 範圍：`App.jsx`、`Header.jsx`、`MorePage.jsx`、`QuickCreateSheet.jsx`、`TimerModal.jsx`。
- 內容：底部改為今天／案件／報價／客戶；右上齒輪與搜尋；移除更多頁；浮動鈕只留 ＋；桌面與手機分頁名稱一致；首次啟動橫幅改白話、可關閉且記住。
- 風險：低（不動資料）。注意桌面版原本缺行事曆入口。
- 驗收：所有原功能仍可在 3 次點擊內到達；＋ 中心點擊開的是快速新增；390 寬無元素互相遮蓋。

### 階段 2：今天＋追蹤一目了然

- 範圍：`utils/cases.js`（`buildWorkQueue`）、`work/**`、`calendar/**`、`today/**`、`CasesPage` 的清單與新增表單。
- 內容：佇列成為唯一來源；月曆讀佇列；案件卡追蹤資訊列；太久沒追自動入列；新增案件追蹤日選填、只產生一筆待辦；完整工作總覽入口移除。
- 風險：中。舊客戶沒有案件但有 `nextDate`，不可從今天消失。
- 驗收：把時鐘調到任一天，清單與月曆該日項目完全相同（寫成單元測試）；首屏 ≥4 張卡；15 天未互動的案件出現在今天。

### 階段 3：報價流程

- 範圍：`quote/**`、`CasesPage` 報價區、`utils/quotes.js`、`buildLegacyCaseSeeds`。
- 內容：§4.3 全部；修正無客戶報價重整後長出「未命名客戶」案件。
- 風險：中。舊報價的「沒有選配」標記要相容；PNG 內容規則不可破。
- 驗收：§5 第 2、4 列步數；全程無原生確認視窗；預覽與 PNG 無利率、成本、內部備忘；無客戶報價重整後案件數不變。

### 階段 4：成交到交車

- 範圍：`deals/**`、`CasesPage` 配件／施工區、`utils/delivery.js`、`utils/stock.js`、密碼相關檔。
- 內容：施工 SOP 移出密碼；金額畫面首次設定密碼；一按完成；缺配件警示；最後一步確認交車並產生回訪提醒（防重複）；完成後狀態一致。
- 風險：高。回訪提醒不可重複建立；舊成交（僅 `case.dealId`）要相容；未加密畫面不得露出成本。
- 驗收：§5 第 5、7 列步數；全新裝置可不輸入密碼走完交車；交車後卡片只顯示完成、提醒各只有一份；既有 `e2e/stock-flow.mjs` 通過。

### 階段 5：客戶頁瘦身與單一入口

- 範圍：`crm/**`、`context.jsx`（最小）。
- 內容：§4.4；一個「加待辦」、一個「記錄聯繫」；移除建立成交案、舊交車表單、看板入口。
- 風險：高。`client.log`、`client.todos` 是整筆覆蓋式同步，改寫入路徑時不可遺失既有項目。
- 驗收：既有客戶的歷程、待辦、照片筆數改版前後一致（以備份檔比對）；客戶詳情長度 ≤2 屏。

### 階段 6：設定分組、用語、文件

- 範圍：`SettingsPanel.jsx`、各檔 UI 字串、`CLAUDE.md`、`docs/**`、`.claude/skills/verify/SKILL.md`。
- 內容：設定三組；用語統一為 配件、廠商、客戶、儲存、回收筒；使用說明重寫；文件中內部成本入口改為「數字密碼」。
- 風險：低。只改顯示文字，不改儲存鍵。
- 驗收：全站搜尋不再出現被淘汰的用語（UI 字串）；文件與程式一致。

### 建議的模型分工

| 階段 | 建議 | 理由 |
|---|---|---|
| 0、1、6 | 中階模型 | 範圍清楚、風險低 |
| 2、3 | 高階模型 | 牽涉佇列邏輯與長表單重整 |
| 4、5 | 最高階模型，且單獨執行 | 涉及資料寫入路徑與相容性 |
| 每階段驗收 | 另一個模型獨立實測 | 避免自己驗自己 |

一次只跑一個階段。先前三組同時執行，三次撞到用量上限而中斷。

## 7. 風險總表

| 風險 | 影響 | 對策 |
|---|---|---|
| 改寫入路徑時覆蓋 `client.log`／`todos` | 掉資料 | 階段 5 前後以備份檔比對筆數；只增不刪 |
| 回訪提醒重複建立 | 今天被洗版 | 以成交 id＋提醒種類去重，寫單元測試 |
| 舊客戶無案件，追蹤日消失 | 漏追客戶 | `nextDate` 唯讀進佇列 |
| 收起入口後找不到功能 | 使用者卡住 | 設定頁三組都可搜尋；使用說明同步更新 |
| 同時改同檔造成合併衝突 | 進度重做 | 一次一階段 |
| 兩台裝置同時改同一客戶只留一邊 | 掉資料（既有問題） | 不在本規格範圍，設計見 `docs/HANDOFF.md` |
